# Hunter's Laws (standing rules, all targets)

1. **In-scope, authorized targets only.** Bounty program, own chain, or testnet. Paste program rules into `scope.md` before any probing.
2. **Raw over summary.** Requests, responses, code, test output — verbatim. Never paraphrase.
3. **One thing per message.** One subsystem, one hypothesis, one probe at a time.
4. **Close the loop.** Always report what happened after a probe — "blocked, 403" is as valuable as a 200.
5. **Kill fast.** 5 distinct dead probes → next test. Log `dead` leads; they prevent re-hunts.
6. **Ledger always updated.** Every lead gets a row in `findings.md`: `testing / dead / dup? / confirmed / reported`.
7. **Proof before report.** A finding ships only with a passing test, a state query, or a priced repeatable trigger — never code-only suspicion.
8. **No destructive mainnet actions.** PoCs run on local devnet or tests. No live validator-set attacks, no DoS volume.
9. **No secrets in files.** Redact keys/tokens; never commit them.
10. **Present before proving.** Show the finding + PoC plan FIRST and get explicit approval before running anything that costs time, storage, or compute. Never surprise-run builds, downloads, or nodes.
11. **Impact bar comes from the program, not a standing ban.** At intake, write the target program's paid impact classes verbatim into `scope.md` (`impact_bar:`). Every DoS/panic/griefing/liveness-only, revert-only, or dust-class dismissal MUST cite that bar (`scope.md` quote showing the class unpaid/OOS). Where the bar is silent or unknown, the standing default holds: fund-loss, theft, freeze-of-funds, or state-corruption classes only — "the tx reverts" is not a finding. A permanent lock of user funds counts as freeze-of-funds regardless of surface shape. Dismissals stay evidence-based: `dead` needs ≥1 probe OR the verbatim bar citation for the class; a claim that carries fund-loss/freeze under any regime the program permits is never closed by reasoning alone.
12. **Economic Attribution Rule.** External data → money-moving transition: walk event → proof → metadata → controller → replay → binding → entitlement. Unbound metadata = candidate. Probe with the mechanism question ("can two attribution mechanisms read the same economic event as two entitlements?"). Full text: `.opencode/skills/universal-testing/refs/economic-attribution-rule.md`.
13. **Equivalent-Entry-Point Diff.** Same economic operation via any alternate path (batch/admin/internal/legacy/...) → diff auth field-by-field → price extraction chain (missing check → victim identity → downstream trust → manufacture counterparty → extract). Full text: `.opencode/skills/universal-testing/refs/equivalent-entrypoint-drift.md`.

14. **No oracle-returns-zero findings.** Banned class, zero exceptions: never propose, probe, intake, or report any finding whose impact requires a price oracle (or price feed / valuation source) to return 0, an unset/zero price, or a missing price. Dead on arrival — do not intake, do not log a ledger row, do not mention it.

15. **Dead-lead residue.** A kill records *what protected the protocol*, not merely that the lead failed. At the moment a lead goes `dead`, write the residue block into its ledger row: economic event → representations A/B → protection with `file:line` → neighboring writers of A/B → **unchecked alternate paths** → offspring → Status (`DEAD` / `FULLY CLOSED` / `TRANSFERRED` / `SPAWNED`). A protection found on the path you proved safe is the comparison that exposes a path nobody checked. Center question: *"What did this dead lead teach me about the protocol that I did not know before testing it?"* — if the answer is nothing, you only killed a hypothesis. Promotion still obeys the 7-field intake; Law 11/14 bars still apply to any offspring. Full text: skill `dead-lead-analysis`.

16. **Four maps, updated at result time.** Every target keeps four maps that feed each other: **coverage** (where auditors actually looked) · **hotspot** (where economically important mechanisms intersect under thin scrutiny — `hotspot-map.md`) · **dead-lead** (what we learned from leads that appeared vulnerable but weren't) · **finding** (where reality already showed the model was incomplete). A confirmed finding reshapes the hotspot — it is not merely marked "found"; a kill fills the dead-lead map and the hotspot's `Neighbors`. The score is an **explanation with evidence**, never a number. A result that leaves all four maps untouched was recorded but not learned. Full text: skill `hotspot-mapping`.

17. **Variant analysis on every confirm.** A finding is a pattern, not an event. On `confirmed`: extract the discriminating characteristics (which representations disagreed, the operator/scale at fault, the missing check, the entry-point class, the constraint that was missing), then grep the codebase AND the audit corpus for them — and ledger the result **even when the answer is "none"**, because "pattern does not recur here" closes a whole class. One finding → N, or a documented closure. Center question: *"What characteristics of this finding define its bug pattern, and where else does that pattern occur?"* Full text: skills `hotspot-mapping` (signature extraction) + `prior-audit-pattern-matching` (codebase + corpus search).

18. **Scope-neutral triage (technical first, scope second).** Never discard a hypothesis because its category (front-running, ordering, DoS, liveness, griefing, gas) is commonly contest-OOS — that is contest folklore, not analysis. Investigate technical validity first (attacker model, preconditions, reachability, impact), then apply the program's ACTUAL rules from `scope.md` verbatim. Every closure carries both a `technical_disposition` (`technically_disproven | technically_plausible | insufficient_evidence`) and a `scope_disposition` (`in_scope | explicitly_oos | conditionally_oos | scope_ambiguous | no_exclusion_found`). Technically-plausible-but-OOS findings go to the OOS register (`oos-register.md`) — never silently killed, never submitted unless the rules support it; `scope_ambiguous` → surface to human review (Law 10), never a silent discard. Consideration ≠ reporting: a valid OOS-class issue is recorded against the impact bar (Law 11), not auto-promoted and not auto-dismissed.

**Master question (12+13):** *What identity/proof authorizes this economic transition, and can I reach it through a path where the binding is weaker?* Comparison-first, never function-first; price the extraction chain before severity.

**Kill question (15):** *What protection killed this lead, and where else does that same protection — or its absence — participate?*

**Map question (16):** *Did this result change what the next lead should be?*

**Variant question (17):** *What is this finding's discriminating characteristic, and where else does it occur?*
